# Staging

Project production is separate on [CT115](../production/README.md). Only an explicit
production request authorizes its manual `origin/main` activation; staging pushes
and preview acceptance do not. Keep appdata and telemetry identities separate.

Blog Alloy and Blackbox collectors remain here; shared Umami/Grafana run on
CT110. Neutral shared URLs are primary; the old staging-suffixed URLs remain compatibility aliases. See the
[observability runbook](blog-observability/README.md).

CT114 `staging` runs trusted development branches independently of production:
Debian 12, 6 CPUs, 16 GiB RAM, 512 MiB swap, 500 GiB replaceable root disk,
static `192.168.0.114`, unprivileged, on boot. Its canonical appdata bind is
`/srv/appdata/docker/staging`. Stillroom has an explicitly authorized narrow
photos/archive exception described below; other apps have no shared media, production appdata,
production `.env`, hardware, remote Docker API, or PVE credentials.

The first app is [film-introspect](https://github.com/rafael-alani/film-introspect/tree/staging)
at **https://film-introspect.staging.rafael.media**, private to LAN/Tailscale.
The API is Docker-internal and web port 8080 binds only the staging LAN IP.
Pi-hole provides the exact local record; NPM uses a dedicated
`*.staging.rafael.media` certificate and a deny-by-default source-address policy.
The route reconciler creates the certificate once with NPM's existing
Cloudflare DNS-01 credentials, then NPM manages renewals. ACME creates temporary
public TXT records; no public application A/AAAA record or router change is
needed. The previous `film-introspect-staging.rafael.media` private route is
retained as a transition alias; the new name is the canonical application origin.

CPU and memory are shared ceilings, not dedicated reservations. The root disk
is a ZFS `refquota` with zero `refreservation`; 500 GiB is not allocated up front
or guaranteed available. At resizing, the host had 407 GiB usable pool space,
18 GiB available RAM, and 8 physical CPU cores. All guests compete for these.
Staging's durable appdata bind is outside its root-disk quota and shares the
same SSD. Keep at least 60–90 GiB SSD headroom, monitor both paths and host RAM
in Pulse, and serialize builds. More storage or reduced existing usage is
required before staging can actually consume 500 GiB. No retained images,
data generations, or snapshots are automatically pruned.

## Push a staging release

The separate private [Staging Homarr board](https://rafael.media/boards/Staging)
is generated by `sync-homarr.py`. PVE's `dothomelab-staging-homarr.timer` reads
CT114's Compose registry and enabled Symphony routes every two minutes, then
updates only this board in CT110. Bootstrap installs the timer for both full
and staging-only runs. New projects appear automatically; disabled Symphony
projects and removed Compose registrations disappear. Retained archives are
not an enrollment source. A failed inventory read leaves the board untouched.

The sync uses PVE's existing guest access; no Homarr credentials or production
mounts reach staging. It preserves all home-board selections and refuses to
manage a public or home board. The board's app tiles and responsive layout are
managed; put custom widgets on another board. Tile descriptions identify the
deployment source, not real-time health, and tile pings are disabled.

On PVE, run `hosts/staging/sync-homarr.py --check` to detect pending changes or
run it without that flag to reconcile immediately. An existing same-name board
requires explicit one-time adoption with `--adopt-board <board-id>`; the normal
timer never assumes ownership by name. Its ownership record is
`/srv/appdata/docker/homarr/staging-board-managed.json`, alongside the canonical
Homarr database. Restore both from appdata. Runtime code is installed in
versioned directories under `/usr/local/lib/dothomelab-staging-homarr/releases`;
the `current` symlink and its `DEPLOYED_COMMIT` identify the active code.
Disable the timer before a software or board rollback; retain prior releases
and avoid restoring the whole Homarr database over subsequent user changes.

Push commits to the app repository's `staging` branch. A guest-local systemd
timer checks `apps.json` every two minutes (up to ten seconds jitter).
It builds the new commit before stopping the old app, validates Compose,
copies the stopped app's data into an independent generation, starts the new
containers, and requires container health, direct UI/API health, and SQLite
integrity before accepting it. Cutover has a brief interruption; this is not
a zero-downtime platform.

App code updates are explicitly authorized by the staging workflow and do not
use WUD or wait for the daily PBS job. Every staging container has
`wud.watch=false`. This is a separate deployment path from production's
backup-gated image updates. Only people trusted to execute code inside this
guest should be able to push these branches. Builds have network access;
the LXC's resource limits contain their CPU/memory use.

On PVE:

```bash
pct exec 114 -- systemctl status dothomelab-staging.timer
pct exec 114 -- journalctl -u dothomelab-staging.service -n 80
pct exec 114 -- /opt/dothomelab/hosts/staging/deploy.py --verify
pct exec 114 -- /opt/dothomelab/hosts/staging/deploy.py --app film-introspect --retry
```

Build failures leave the current app running. A failed health check restores
the previous containers and their untouched data generation. The failed
commit/configuration is held until a new commit/configuration arrives or an
operator passes `--retry`. A persisted deployment journal recovers interrupted
cutovers. A failed attempt never deletes databases, volumes, images, source
bundles, or rollback generations. Those accumulate and need separately
reviewed cleanup; keep an eye on staging root and appdata capacity in Pulse.

To pause updates, disable the timer with
`pct exec 114 -- systemctl disable --now dothomelab-staging.timer`. This does
not interrupt an in-progress service run. A normal Git revert pushed to
`staging` deploys against current data; schema-incompatible downgrades require
an explicit choice of a retained data generation. Do not blindly switch the
current pointer to an older generation after users have added notes.

## Film-introspect settings

Film-introspect asks Meta Egg to discover movie metadata online, then find
English subtitle releases for the selected film. Wikidata metadata needs no
account. OpenSubtitles needs the dedicated application key described below;
missing configuration, no subtitle matches, and provider failure appear as
separate states. The licensed **Sintel (2010)** catalog remains available for
trying the complete workflow without credentials. The app clock is aligned
manually with a film playing on another screen. Focusing a note holds its
timestamp and subtitle view while the clock advances; saving catches up. The
[user manual](../../USER_DOC.md#take-notes-during-a-screening) owns the controls.
A cinema or friend's screen requires no Jellyfin connection.

`initialize-env.py --app film-introspect` generates a dedicated
`STAGING_FILM_INTROSPECT_AUTH_SECRET` in PVE `/root/.env` and renders only its
explicitly prefixed variables. Use `STAGING_FILM_INTROSPECT_DEMO_MODE=false` and
`STAGING_FILM_INTROSPECT_META_EGG_URL=http://192.168.0.114:8085`. Notes remain in
the existing independent SQLite data generations; legacy direct-Jellyfin notes
are not silently merged into Meta Egg timelines. Do not restore an old data
generation over notes added since that release.

## Meta Egg screening API

[Meta Egg](https://meta-egg.staging.rafael.media) follows its private repository's
`staging` branch on CT114 port 8085. Its root `Dockerfile` owns container port
3000 and `/health`. Homelab sets `SCREENING_ONLY=true` and
`SCREENING_PROVIDER=discovery`: catalog matches keep their existing identity;
other titles are searched through Wikidata. Selecting a discovered film starts
an English subtitle-release lookup through OpenSubtitles using the film's IMDb
identity. Release labels describe subtitle versions, not a detected editorial
cut. The selected subtitle file supplies original timed cues.

Set `STAGING_META_EGG_OPENSUBTITLES_API_KEY` in PVE `/root/.env` to a dedicated
OpenSubtitles.com application key. Create an account and register the application
through [OpenSubtitles consumers](https://www.opensubtitles.com/en/consumers).
The key alone enables anonymous API access with provider download limits; no
Jellyfin credential is required. The initializer renders only this scoped value
as `OPENSUBTITLES_API_KEY` for Meta Egg. Film-introspect and browser clients never
receive it. Re-render Meta Egg's environment and deploy after changing it. An
empty key leaves metadata discovery available and reports subtitle setup as
missing; it never fabricates a transcript or falls back to another film.

Homelab mounts only the application's independent `STAGING_DATA` generation at
`/data` and sets `SCREENING_DATA_DIR=/data/screening`. Selecting a discovered film
saves its metadata; loading a selected subtitle saves that exact release and its
original timed cues. Saved records survive process restarts and staging updates,
and repeated reads reuse the saved transcript without another download. This is
a private screening library, not activation of Meta Egg's canonical graph or
storage of the movie video. Failed downloads remain unavailable.

The generation is owned by guest root (PVE unprivileged UID 100000), matching the
staging deployer's copy ownership. Meta Egg uses that UID only in this deployment,
with all capabilities dropped, no privilege escalation, a read-only root
filesystem and a bounded temporary directory. No media or Docker socket is
mounted. Only root/health and screening GET routes are exposed; selecting a film
or transcript can write its screening record, and a first transcript GET can
spend an OpenSubtitles download allowance. Unrelated mutation routes remain
disabled. NPM keeps LAN/Tailscale restrictions; this unauthenticated MVP must
remain private. Subtitle source terms and attribution are retained, without
claiming an open redistribution license. The existing catalog source evidence
remains in the [standalone pilot](../../docs/evidence/2026-10-22-screening-standalone-pilot.md).

The existing deployer stops the old app and copies its data into a fresh release
generation before cutover; previous generations remain available. A code rollback
must preserve current saved screening records, just as Film-introspect rollback
must preserve notes. Scheduled appdata backups cover this path; no new restore
claim is implied.

Publish both app candidates to their `staging` branches, render their scoped
environments on PVE, then sync the committed homelab archive. Meta Egg uses its
retained dedicated read-only GitHub deploy key. Deploy it before Film-introspect:

```sh
hosts/staging/initialize-env.py --app meta-egg
hosts/staging/initialize-env.py --app film-introspect
pct exec 114 -- /opt/dothomelab/hosts/staging/deploy.py --app meta-egg
pct exec 114 -- /opt/dothomelab/hosts/staging/deploy.py --app film-introspect
pct exec 114 -- /opt/dothomelab/hosts/staging/deploy.py --app meta-egg --verify
pct exec 114 -- /opt/dothomelab/hosts/staging/deploy.py --app film-introspect --verify
```

Each application's exact source commit, scoped environment, image and prior
release are retained independently. Process health is followed by an actual
movie/cut/subtitle lookup and a note test while the real film keeps playing.
The separate movie clock must keep advancing while the note is held; the saved
timestamp must retain its original value and the subtitle view must catch up.
No new media mount, database engine or on-demand PBS backup is needed.
Scheduled appdata coverage does not establish a clean-host restore or user
acceptance. Subtitle alignment and catalog breadth remain explicit limits.

### Optional Jellyfin provider

Jellyfin is not a prerequisite for the standalone screening workflow. An operator
can deliberately change the app's provider to `SCREENING_PROVIDER=jellyfin` for
library metadata, text subtitles and visible-session observations. Only then
supply `STAGING_META_EGG_JELLYFIN_URL`, `STAGING_META_EGG_JELLYFIN_API_KEY` and
`STAGING_META_EGG_JELLYFIN_USER_ID` and render Meta Egg's scoped environment.
Film-introspect and the browser do not need that credential. Missing optional
configuration must remain an unavailable integration, not a fallback demo.

The maintained account initializer accepts an explicit owner-only administrator
token file on PVE; it is not run by bootstrap or the catalog preview:

```sh
python3 scripts/initialize-meta-egg-jellyfin.py \
  --admin-token-file /run/meta-egg-jellyfin-admin.token \
  --url http://192.168.0.112:8096 --env-file /root/.env
```

It creates hidden non-admin `meta-egg-staging` with access only to movie libraries,
disables destructive/management/control/sharing/transcoding permissions, verifies
the resulting policy, and saves only the dedicated user's credentials. It never
discovers credentials, follows redirects or prints secrets/API bodies. The
recovery password stays in PVE `/root/.env` and is not rendered to containers.
Saved password, user ID and token support interrupted-creation recovery and
idempotent retries; same-name accounts without ownership proof or changed
server/user identity fail closed. Retain those values for recovery. Disable the
dedicated account to withdraw optional access. The initializer's tests use
fixtures; no live Jellyfin provisioning is claimed by the standalone pilot.

## Add another app

1. Add a credential-free GitHub repository URL, branch, unique port, private
   `app.staging.rafael.media` hostname, HTTP health path (optional JSON success key),
   Compose path, SQLite filenames, and container
   count to `apps.json`. A missing branch fails closed; main is never a fallback.
2. Add a reviewed Compose definition under `hosts/staging/<name>`. Follow the
   sample's `STAGING_SOURCE`, `STAGING_IMAGE_TAG`, `STAGING_COMMIT`,
   `STAGING_DATA`, and `STAGING_ENV` variables; name it `staging-<name>`.
   Only mount the app's data generation. Give every service a health check,
   resource/log limits, `wud.watch=false`, and the commit label. The runner
   checks `/` and the declared health endpoint; the sample requires JSON
   `{"ok":true}` at `/api/health`.
3. Extend the initializer to render that app's scoped runtime environment.
   Stateless apps can declare `sqlite: []`; SQLite apps list their database
   filenames. Other database engines require a new application-consistent
   backup/restore implementation and verification before enrollment.
4. Commit/push homelab configuration, then run `./bootstrap.sh --staging-only`
   from the updated PVE clone. This syncs the reviewed definitions, creates
   missing CT114 only, deploys registered apps, adds private DNS/TLS routes,
   updates the backup freeze list and Pulse, and runs focused verification.
   Existing production Compose projects are not redeployed.

The currently installed implementation uses Git declarations and branch polling.
The [deployment architecture research](../../docs/staging-platform-research-2026-10-04.md)
compares shared Actions workflows, self-hosted runners, and deployment dashboards.
No GitHub credential
is needed for the public test repository. Private repositories need a
separately scoped read-only credential/recovery design before enrollment.

## Recovery inputs and limits

Full `./bootstrap.sh` includes CT114. For an existing homelab use:

```bash
./bootstrap.sh --staging-only --dry-run
./bootstrap.sh --staging-only
./hosts/staging/verify.sh
```

Canonical appdata contains each app's `current.json`, `previous.json`, optional
`pending.json`/`failed.json`, scoped environment, and `releases/<id>/` with
Compose, source Git bundle, environment, commit metadata, and independent
`data/`. The entire tree is inside the existing encrypted appdata backup;
CT114 joins its short freeze window. No on-demand PBS job is needed for a
new empty deployment. Inclusion does not prove a later PBS backup or restore.

Guest root source checkouts, Docker images, and build cache are replaceable.
On recovery the accepted commit is rebuilt from its retained Git bundle before
checking GitHub for a new branch head. Registry access and upstream base
images remain external rebuild prerequisites; previously built images are
retained locally but are not exported into appdata. Film-introspect's staging
Dockerfiles install from the frozen Bun lockfile. Dependency/base-image
availability and a complete clean-host rebuild remain unverified externally.

An interrupted candidate never becomes current until all checks pass. SQLite
generation tests cover corruption, symlinks, build failures, health failures,
and crashes before/after the current-pointer commit. Live acceptance evidence
belongs in `docs/staging-addition-2026-10-04.md`.

## Coordinated project removal

Use Symphony's `agentctl project plan owner/repository --profile /absolute/path/profile.json`
on the operator Mac, then apply its exact approval hash. A completed retirement
precedes a fresh `--mode purge` plan. The controller coordinates the Mac, VM101,
PVE/CT114, CT110 and GitHub, retaining its progress when a host is unavailable.
The owning procedure is Symphony's `docs/project-lifecycle.md`; its profile is
`examples/project-lifecycle.json` in the Symphony checkout.

The matching lifecycle helpers and Symphony worker/bridge/preview changes are
required. This repository supplies the Compose, initializer, NPM and Homarr
barriers. Persistent repository records in
`/srv/appdata/docker/staging/retired/<repository-sha256>.json` override an app's
Git declaration, so a restored `apps.json` cannot redeploy a retired project.
CT110 also records exact retired hostnames in
`/srv/appdata/docker/infra-nginx-proxy-manager/staging-retired-hosts`.
Restore these canonical appdata records before enabling automation.

Retirement stops the app and removes its owned routes and managed dashboard
entry; GitHub is archived. Purge moves exact source/appdata copies into named,
verified `.symphony-retired/<operation>/` directories before deleting GitHub.
It never uses `down -v`, prunes images or volumes, edits import receipts, deletes
user notes, or destroys shared backup history. Those retained copies are listed
in the operation report. Re-enrollment and rollback-history erasure require a
separate reviewed operation; do not delete barriers to clear an incomplete step.

## Stillroom external-library archiving

[Stillroom](https://stillroom.staging.rafael.media) tracks the private
`rafael-alani/immich-external-library-picture-removal` repository's `staging`
branch on port 8083. The user explicitly authorized this staging app to use
production Immich and shared originals for dummy-album acceptance. Its dedicated
read-only API key is `STAGING_STILLROOM_IMMICH_API_KEY` in PVE `/root/.env`;
permissions are `asset.read`, `library.read`, `user.read`, `album.read` for the
administrator who owns the library. Initialization copies only that prefixed
key and `STAGING_STILLROOM_IMMICH_URL` to its private runtime environment.

The exception is exactly CT114 mp1 `/vault/shared/media/photos` →
`/shared/media/photos` and mp2 `/vault/shared/archive` → `/shared/archive`.
Only the Stillroom container receives those binds: photos at `/old-photos`
(the production Immich API path), archive at `/archive`. It runs as guest
1000:1000 (PVE 101000:101000). Production Immich's originals remain read-only.
No whole-shared-tree, production appdata or hardware mounts are added to CT114.

The tracked config template initializes a persistent config only when absent:
`/srv/appdata/docker/staging/stillroom/config.json`. It selects the observed
library UUID, `trigger: trash`, owner albums starting exactly `Archive:`, a
five-minute undo grace, three successful observations, 30-second polling and
20 bundles per scan. Live moves are configured but remain gated until the user
selects and trashes a disposable compatibility sample in Activity. The sample
is retained. Existing trash and unrelated albums do not qualify.

Create an `Archive: dummy test` album, wait for **tracking**, select one sample,
trash it, and wait for **verified**. Restore that sample in Immich; trash different
dummy items to test actual moves. Leave them in trash until **archived**. The
archive is `/shared/archive/temp/<timestamp>-<album>/photos/<original paths>`
in CT114, `/vault/shared/archive/temp` on PVE. Move completed batches into
`archive/body-update` between runs; keep the archive root stable. The application
[handbook](https://github.com/rafael-alani/immich-external-library-picture-removal/blob/staging/USER_DOC.md)
owns detailed workflow and restore instructions.

Unlike ordinary staging databases, Stillroom's `state/tracker.sqlite3` is
**stable across releases**. File moves cannot be rolled back by restoring a
previous tracker generation. The deployer verifies its SQLite integrity and
allows up to one hour for graceful shutdown; interrupted operations retain a
journal and block retries. Retain the stable state on code rollback. Restoring
old tracker backups requires reconciling all later file moves first. Appdata
backup includes this tracker, but `/vault/shared` remains outside PBS coverage;
archiving within that pool is not a backup.

PVE setup (after reviewing source and committing the deployment):

```sh
hosts/staging/initialize-env.py --app stillroom
hosts/staging/stillroom/prepare.sh
# Sync this committed homelab revision to CT114, preserving prior archives.
pct exec 114 -- /opt/dothomelab/hosts/staging/deploy.py --app stillroom
pct exec 114 -- /opt/dothomelab/hosts/staging/deploy.py --app stillroom --verify
```

`prepare.sh` creates only the exact missing archive/state directories and uses
PVE's additive bind-mount hotplug. It refuses conflicting mounts/owners; it does
not recursively change existing photos. Bootstrap declares the same mounts.
To pause archiving during manual work, stop this app's `archiver` service and
pause the staging poller, which otherwise restarts unhealthy apps. Preserve all
release directories and archive files. Resume the poller when the service is
ready; do not leave unrelated apps permanently without their update checks.

### Private staging repositories

A registry entry with `private: true` uses only its dedicated read-only GitHub
deploy key under `<app>/git/id_ed25519`. The SSH host keys come from GitHub's
HTTPS metadata endpoint and are pinned in the adjacent `known_hosts`; strict
host checking stays enabled. The application container receives neither file.
Existing public repositories continue anonymous HTTPS fetching.

For a newly enrolled private repository, run `initialize-repo-key.py --app NAME`
on PVE after environment initialization, register only its `.pub` as a read-only
repository deploy key, then deploy. Retain this directory in canonical appdata
backups. If absent during a rebuild, GitHub registration is an external
prerequisite; never substitute personal or PVE credentials. Stillroom uses this
mechanism. GitHub key rotation/revocation requires an explicit operator change.
